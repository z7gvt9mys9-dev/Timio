# CLAUDE.md — правила для работы над SlotMarket

Эти правила обязательны. Если правило мешает выполнить задачу, остановись и спроси, а не обходи его.

## 1. Перед любой работой

1. Прочитай `PLAN.md` целиком, до первой правки кода. Это единственный источник истины по проекту (идея, ТЗ, модель данных, статусы, формулы, границы MVP).
2. Найди в `PLAN.md` раздел, к которому относится задача (например, B4.4 для цены, B7 для таблиц), и работай строго по нему.
3. Если `PLAN.md` и мои слова в чате расходятся, остановись и покажи расхождение. Не выбирай сам.
4. Если в `PLAN.md` нет ответа или требование неоднозначно, задай один короткий вопрос. Не придумывай поведение.
5. Если задача меняет решение из `PLAN.md`, сначала предложи правку `PLAN.md`, потом код.

## 2. Объём работы: ничего лишнего

- Делай только то, что просили. Ни фич «на вырост», ни «заодно улучшил».
- Не добавляй функции, поля, таблицы, команды, статусы и эндпоинты, которых нет в `PLAN.md`.
- Не делай то, что `PLAN.md` относит к «Не входит в MVP»: онлайн-оплата, мобильное приложение, регистрация и бронирование на сайте, интеграции с YClients и Dikidi, несколько городов, отзывы.
- Не добавляй новые зависимости без согласования. Стек зафиксирован: Python 3.12, aiogram 3, SQLAlchemy 2, SQLite (WAL), APScheduler, FastAPI, Jinja2, Tailwind, Alpine.js.
- Не рефакторь код, который не относится к задаче. Не переименовывай и не переставляй чужие файлы.
- Не создавай абстракции, базовые классы, фабрики и конфигурации «на будущее», пока нет второго места использования.
- Не пиши документацию, README, примеры и скрипты, которые не просили.
- Не делай `git commit`, `git push` и не трогай ветки, пока не попросили.
- Одна задача — один небольшой понятный diff. Если правка выходит за ~200 строк, предложи разбить.

## 3. Стиль кода

Основа: **Google Python Style Guide**, поверх PEP 8. Весь код в проекте выглядит так, будто его писал один человек.

### Форматирование

- Отступ 4 пробела. Длина строки до 80 символов.
- Кавычки двойные `"`. Одинарные только внутри строки.
- Две пустые строки между функциями и классами верхнего уровня, одна между методами.
- Импорты в начале файла тремя группами: стандартная библиотека, сторонние, свои. Внутри группы по алфавиту. Только полные пути, без `from x import *` и без относительных импортов.
- Импортируй модули и классы, не отдельные функции, если так читается яснее: `from core import pricing`, затем `pricing.calc_price(...)`.

### Имена

| Что | Формат | Пример |
|---|---|---|
| Модуль, пакет, функция, переменная | `snake_case` | `calc_current_price` |
| Класс | `CapWords` | `SlotService` |
| Константа | `UPPER_SNAKE_CASE` | `MIN_PRICE_SHARE` |
| Приватное | префикс `_` | `_round_price` |

- Имя говорит, что это. Без `data`, `tmp`, `x`, `res`, `obj`, `info`.
- Функция называется глаголом: `create_slot`, `cancel_booking`. Булево — вопросом: `is_open`, `has_active_booking`.
- Аббревиатуры не вводить. Исключения: `id`, `tg`, `db`, `url`.
- Имена в коде на английском. Тексты для пользователя (сообщения бота, страницы сайта) на русском.

### Функции и классы

- Функция делает одно дело и помещается на экран (до ~40 строк). Длиннее — раздели.
- Не больше 4–5 параметров. Больше — передай объект или dataclass.
- Не используй изменяемые значения по умолчанию (`def f(x=[])`).
- Ранний `return` вместо глубокой вложенности. Не больше 3 уровней вложенности.
- Нет «магических чисел» и строк: `30`, `0.15`, `"booked"` выносятся в именованные константы или `Enum`. Статусы из раздела B7 — только через `Enum`.
- Тип-подсказки обязательны для всех параметров и возвращаемых значений. `Optional` пиши как `X | None`.
- Для данных с полями используй `dataclass`, не словари и не кортежи.

### Docstring и комментарии

- Docstring в формате Google (`Args:`, `Returns:`, `Raises:`) у каждой публичной функции и класса. Первая строка — одно предложение, что делает.
- Комментарий объясняет **почему**, а не **что**. Код, который понятен сам, не комментируется.
- Не оставляй закомментированный код, `print` для отладки и `TODO` без номера пункта из `PLAN.md`.
- Язык docstring и комментариев: русский, коротко.

### Ошибки

- Ловить конкретные исключения. Голый `except:` и `except Exception:` без повторного `raise` или логирования запрещены.
- Ошибки пользователя (неверная цена, дата) — понятное сообщение с примером формата, как в B9. Ошибки системы — в лог.
- Не глотай ошибки молча.

## 4. Архитектура (из B6, не нарушать)

- `bot/handlers/` — только приём ввода, проверка формата и вызов сервиса. **Бизнес-логики в обработчиках нет.**
- `core/` — вся логика: `calculator`, `pricing`, `slots`, `bookings`, `reports`, `feed`. **Модули `core/` не импортируют aiogram, FastAPI и ничего про Telegram.**
- `web/` и `bot/` вызывают `core/`. Формулы калькулятора и цены существуют в одном месте. Копировать их в сайт или обработчик нельзя.
- `db/` — модели и сессии. Прямые SQL-запросы вне `core/` и `db/` запрещены.
- Структуру проекта из B6 не менять без согласования.

## 5. Жёсткие правила предметной области

- **Время:** в базе всегда UTC, пользователю показывается время города. Наивные `datetime` запрещены, везде `tz`-aware.
- **Деньги:** целые рубли (`int`) или `Decimal`. Не `float`.
- **Бронирование:** только атомарным обновлением `UPDATE slots SET status='booked' WHERE id=? AND status='open'`. Проверка «сначала SELECT, потом UPDATE» запрещена.
- **Переходы статусов слота:** только те, что в таблице B7. Остальные запрещены.
- **Цена в брони:** фиксируется в `bookings.price` в момент брони и дальше не пересчитывается.
- **Скрытое название:** при `hide_name = true` название и адрес не попадают ни в пост канала, ни на страницу, ни в ответ API до брони. Проверяется тестом.
- **Персональные данные:** только имя, Telegram ID, телефон. Телефон покупателя виден владельцу только после брони. Не логируй телефоны.
- **Секреты:** токен бота и ID администраторов только из `.env`. Не коммить `.env`, не печатай токены в лог.
- **Сайт:** без регистрации, без паролей, без хранения имени и телефона. Бронь только через deep link в бота.
- **Комиссия:** в MVP не взимается, только считается справочно.

## 6. Тесты

- Каждая правка в `core/` идёт вместе с тестом `pytest` в `tests/`.
- Обязательные тесты берутся из B11: цена (начало, середина, последние 2 часа, поздняя публикация, округление), формулы калькулятора на примере из B4.1 (312 пустых часов, 468 000 ₽, 29 250 ₽), гонка двух покупателей, лимит броней, отмена, блокировка после неявок, переходы статусов.
- Тест проверяет поведение, а не реализацию. Одно утверждение — одна идея. Имя: `test_<что>_<при каком условии>_<результат>`.
- Перед тем как сказать «готово», запусти тесты и покажи результат. Если не запускал, так и напиши.

## 7. Как отвечать и отчитываться

- Коротко: что сделано, какие файлы изменены, что проверено.
- Не пересказывай код, который я и так вижу в diff.
- Если что-то не сделано или не проверено, скажи прямо. Не пиши «всё работает», если не запускал.
- Если нашёл проблему вне задачи (баг, противоречие в `PLAN.md`), сообщи отдельной строкой и не исправляй без разрешения.
